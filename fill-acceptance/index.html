Fill Acceptance Measurements

vibium fill reports success for a value the field cannot hold. The write goes through the native value setter, which throws nothing — so the only question is whether the tool notices the value did not stick. Every value on this page was read back from a live field, not inferred from source.

silent covers two outcomes, and the second is the quieter one: the field is either left empty (number, the date family) or moved to a substitute the browser picked — notacolor becomes #000000, abc on a slider becomes 50. An empty required field usually surfaces at submit; a plausible substitute does not surface at all.

The check cannot be a literal round trip, and that is the whole design. Comparing the value back byte-for-byte reports healthy writes as failures: a range snaps to its step (55 → 60) and clamps to its bounds (150 → 100); a datetime-local folds 2020-01-02 10:30 to the T form and drops a trailing :00; a color expands #abc to #aabbcc. All five were stored. So each family is asked what it can answer: number and the five date types can hold the empty string, so a rejection shows directly as an empty field after a non-empty write; range and color always hold something, so they are asked whether the value was a number, or a #rgb/#rrggbb color, at all.

Normalization is deliberately not an error. Stripping a line break from a text input, trimming an email, folding CRLF in a textarea and lowercasing #00FF00 all still succeed. So does fill "", which clears the field — behavior issue #187 established, and the same builder serves clear.

Not validating is the majority behavior. Playwright is the outlier that gets it right; Selenium is as silent as vibium. So the argument for closing this gap is the spec plus the empty field, not that everyone else already does it.

Selenium has no fill, so the comparison is sendKeys, and the two are not the same operation. For date it is a fair test — the browser renders it as something other than a text input, so Element Send Keys takes the branch that is supposed to report bad input, and does not. For number the keys are simply typed and the browser drops the non-numeric ones (sendKeys("1a2") yields "12"). The week cell shows the difference plainly: the digits landed in segments and produced a valid week, 2099-W20, rather than nothing.

Measured on all five Vibium surfaces — CLI, MCP, and the JavaScript, Python and Java clients — across both engines and both builds. Sixty runs, and all five agree in every combination. Each client raises its own type: Error, BiDiError, VibiumException.

Why the field can reject a value with nothing in the codebase noticing: FillableInputTypesJS (actionability.go:179) is the one place Vibium models input types, and it answers a single question — may fill set this value. color and range sit in that list yet silently substitute. The same one-boolean model is why type has a matching defect of its own.

Type Append Measurements

vibium type and press are documented as appending to a field's existing value. On seven input types they do not. Every value on this page was read back from a live field, not inferred from source.

upstream dd48732 · also reproduced at e63bb73
chrome 152.0.7977.54
firefox 155.0
playwright 1.63.0
selenium 4.49.0 (BiDi on)

Each field is seeded, then type "99" appends to it. Fields are pinned to width:100px because the splice index is the character nearest the center of the box — at width:400px the center falls past the end of the text and the same commands append correctly on both engines. Vibium ran on Chrome and Firefox; Playwright and Selenium on Chrome only, driving the same Chrome binary, because Playwright cannot launch a stock Firefox — it needs its own patched build.

The colors track data loss, not contract. prepended is positional: every character seeded is still there, just not where Vibium's docs promise — gray even though it fails the append contract, and for Playwright and Selenium it fails no contract at all. The two red states destroy what was in the field. spliced at least looks wrong: 123456997890 is visibly mangled. segment overwritten is the more dangerous one — a segmented date input has no string to append to, so each keystroke replaces the segment holding focus, and 2020-01-02 becomes 2020-09-09: a perfectly valid date that passes every check downstream, silently not the one you had. Which segment is hit depends on where the focusing click landed, which is why the same press 5 gives 0005-01-02 at Chrome's default width and 2020-05-02 at width:100px.

Shaded rows are controls. They are the reason the rest of the table can be read: Selenium appends on text and Playwright does not, which is the WebDriver caret rule showing up in exactly one of the two.

No tool here appends on number or email. Selenium lands at offset 0 just as Playwright does — identical at 60px, 100px and 400px, so it is a caret at the front, not a click-point splice. Measured through Selenium, setSelectionRange on a number input throws InvalidStateError and selectionStart reads null, which is the same limitation this report is about. The patch would make Vibium the only one of the three tools that appends.

Prepending is not a bug for Playwright or Selenium. Neither documents type as appending; Vibium does, in three places — element.ts:109, Element.java:58 and SKILL.md:134. That is what makes the same landing position a contract violation here and ordinary behavior there.

And the comparison cuts both ways. On the five segmented types the patch makes Vibium the only one of the four that refuses to write at all — Playwright and Selenium both overwrite a segment and report success, exactly as stock Vibium does. The case for refusing anyway is that they do not promise to append and Vibium does, and that a valid-looking wrong date is worse than a failure; but that is a judgment, and the two halves of the patch are independent if parity is weighed differently.

Firefox renders month and week as plain text inputs — el.type reports text — so they append correctly there and the patch correctly leaves them alone, exiting 0 rather than refusing.

Blast radius. Re-running a 24-element × 2-width × 2-action sweep against stock and patched and diffing every cell: 16 of 96 change on Chrome, 10 on Firefox, and nothing else moves — no color, range, checkbox, file or button cell shifts. Firefox changes in six fewer cells because month and week are text inputs there (four cells) and its default-width number box is wide enough that the value never reaches the click point (the other two).

Why these two types and not the whole list: FillableInputTypesJS (actionability.go:179) is the one place Vibium models input types, and it answers a single question — may fill set this value. number and email sit in that list beside text yet cannot carry a caret, so nothing in the codebase can tell them apart. The same one-boolean model is why fill has a matching defect of its own.

Patch: 3 files, +214/−19; applies clean at dd48732 and at e63bb73. The swap it uses is observable in exactly one way — a MutationObserver on attributes sees type, type where stock sees nothing. Events fired, min/max/step and validity, valueAsNumber, decimals, empty fields and name/form association are all unchanged.

Splice indices are the character nearest the center of the field, so they move with font metrics and widget widths — the verdicts do not.
